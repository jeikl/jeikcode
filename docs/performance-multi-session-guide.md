# 性能与多会话架构优化指南

> 依据:atomcode-crates 源码核查(索引持久化、CodeIndex 并发模型、daemon 进程架构、检索热路径)
> 目标场景:**服务端/客户端 HTTP CLI + 30-40 并发会话 + 读多写少(绝大多数会话是查询/解答类,写代码的核心会话仅 1-2 个)**

---

## 一、现状核查(代码证据)

### 1.1 索引持久化

| 项 | 现状 | 位置 |
|---|---|---|
| 主索引 | `.atomcode/codegraph/units.v3.json`,**纯 serde_json** | `index.rs:37` `DISK_CACHE_REL` |
| 序列化 | `serde_json::to_vec` 全量序列化 + tmp+rename 原子写 | `index.rs:901-904` |
| 反序列化 | `serde_json::from_slice` + `rebuild_name_index` | `index.rs:870-875` |
| 版本 | `DISK_CACHE_VERSION = 3`(版本不匹配即丢弃重建) | `index.rs:34` |
| sqlite | **无**(零数据库依赖) | Cargo.toml 核查 |
| 检索 sidecar | `dirindex` 惰性内存构建;**stats/BM25/概念向量无落盘** | retrieval/ |

### 1.2 并发模型

| 场景 | 现状 | 问题 |
|---|---|---|
| 同进程多会话 | 每会话 runtime 各 `new CodeIndex`(`parts.rs:309`/`assemble.rs:233`) | **N 会话 = N 份内存图**,N=30-40 时内存浪费 30-40 倍 |
| 同进程并发 get | single-flight + Condvar(`index.rs:1242+`),已测并发 8 线程共享同一图 | ✅ 良好,可支撑更高并发 |
| 跨进程 | 磁盘原子写但**无文件锁**,后写覆盖先写 | 偶发重复重建,不损坏但浪费 |
| 后台刷新 | 2 秒轮询 + 指纹比对,未变零成本 | ✅ 良好 |

### 1.3 检索热路径瓶颈(按影响排序)

1. **每次查询重算**:开 BM25/概念向量后,`IdfStats::build(&graph)` 对全量符号(实测 34 万)+ 逐符号 `concept_projection` —— O(N) 每查询;
2. **冷启动慢**:几十 MB JSON 反序列化 + 重建 by_name 索引;
3. **init 全量重写**:改 1 个文件也 `serde_json::to_vec` 全量写盘;
4. **评分单线程**:`score_workspace_symbols` 串行遍历全符号。

## 二、目标场景分析(30-40 并发,读多写少)

```
30-40 个并发会话
├─ 28-38 个:查询/解答类(读)—— code_explore / repo_map 为主
│    ├─ 每次查询 = 加载/复用索引 + 检索 + 评分(当前每会话独立 CodeIndex → 重复加载 N 份)
│    └─ 弱模型 + 读密集 → 检索慢直接放大 N 倍
└─ 1-2 个:编程写代码类(写)—— bash/edit/write 为主
     └─ 写 → 文件变更 → 索引增量刷新(指纹比对,只重解析变更文件)
```

**关键推导**:
- 读会话占比 >90%,**索引加载与检索是瓶颈**,写刷新(增量)几乎无压力;
- 每会话独立 CodeIndex → 30-40 份内存图 + 30-40 次冷启动反序列化,是最大的浪费;
- 读多写少 → **单例共享索引 + 只读缓存** 完美契合(写刷新由 single-flight 收敛)。

## 三、优化方案(按收益/成本比排序)

### P0-A:检索统计/向量 sidecar 落盘(最高性价比)

- **目标**:消除"每查询重算 34 万符号";
- **做法**:构建期一次性算好 `stats.v1.bin`(IDF 表 df/total/avgdl + 每符号概念向量 + BM25 字段统计),查询期 `get_dirindex` 同款惰性加载 + `Arc` 缓存,文件指纹未变即复用;
- **改动面**:`retrieval/{stats,bm25,concepts}.rs` 各加 `save/load`,`index.rs` 构建后触发一次;
- **收益**:开 BM25/概念向量后,code_explore 查询耗时从秒级 → 毫秒级。

### P0-B:daemon 全局单例 CodeIndex(多会话核心)

- **目标**:消除 N 会话 N 份内存图;
- **做法**:daemon 启动时建一个共享 `Arc<CodeIndex>`,`prepare_coding_parts`/`assemble` 注入同一个实例而非各 new;
- **收益**:30-40 会话共享 1 份图 + 1 份 sidecar 缓存,内存省 30-40 倍,首次构建一次全命中;
- **注意**:CodeIndex 内部已有 Mutex+Codvar 并发安全,共享后天然 single-flight。

### P1-A:二进制序列化 + zstd 压缩

- **目标**:冷启动 10-50× 提速;
- **做法**:新增 `units.v4.bin`(bincode/postcard)+ zstd(Cargo.toml 已有 `zstd` 依赖,零新增);版本号区分,保留 v3 JSON 读取做降级;
- **收益**:体积 5-10× 小,反序列化 10-50× 快,冷启动秒级 → 毫秒级。

### P1-B:增量保存 + 磁盘写锁

- **目标**:消除 init 全量重写 + 跨进程覆盖;
- **做法**:仅 `reparsed>0 || removed>0` 才重写(`index.rs:942` "Always rewrite" 改条件写);重建时加 `fs2` 文件锁(依赖已有,optional);
- **收益**:日常改动后 init 从全量序列化 → 跳过/增量;多进程并发安全。

### P1-C:dirindex 显式落盘 + 查询结果缓存

- **目标**:目录全景毫秒级 + 同查询二次命中零开销;
- **做法**:init 时强制写 `dirindex.v1.json`(实现已有,补显式保存);加"同 (graph 指纹, 查询) → 结果缓存"(可与 SESSION_SENT_SPANS 并行);
- **收益**:六类目录全景从内存重建 O(文件数) → 磁盘直读;重复查询零重算。

### P2:并行评分 + walk 快速路径

- **目标**:评分提速 N 核;
- **做法**:`score_workspace_symbols` 用 rayon 并行(图只读安全);`collect_files` 缓存目录 mtime 快速路径;
- **收益**:34 万符号评分从串行秒级 → 并行毫秒级(多核)。

## 五、sqlite 的定位(明确结论)

**现阶段不需要把索引改为 sqlite**。理由:

- 使用模式是"单 daemon 进程内、多会话读共享、写极少" —— sqlite 的并发写/事务/复杂 SQL 价值用不上;
- 三个瓶颈(冷启动/重算/全量写)用二进制 + sidecar + 条件写就能解决,与存储引擎无关;
- 图结构塞关系表要建多表 join,反而复杂。

**只有当以下信号出现时才重新评估 sqlite**:
1. 多进程同时**写**索引(不是现在这种读多写少);
2. 百万级+ 符号,内存装不下需磁盘索引/分页;
3. 需要语言×目录×符号类型×边类型的多维复杂组合查询;
4. 会话数据需要增量 append + 崩溃恢复(那是会话层,pi/opencode 已在做,索引层不需要)。

---

## 六、一句话总结

> 保持"进程内单例 `Arc<CodeIndex>` + JSON/二进制原子文件缓存 + 只读检索 sidecar"的架构:**S1(S2)消除多会话内存重复与查询重算、S3 提速冷启动、S4 避免全量写与覆盖**,就足以支撑 30-40 会话读多写少场景;sqlite 留到"多写 + 百万符号"信号出现再评估。
